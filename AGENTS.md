# AGENTS.md — правила работы для AI-агентов

> Этот файл — инструкция для AI-агентов (Hermes, Claude Code, Codex и т.д.),
> работающих с этим репозиторием. Читай его перед любыми изменениями.

## 1. Обзор проекта

**warehouseHelper** — веб-приложение для автоматизации складских операций:
синхронизация заказов из API МойСклад, экспорт в Excel и PDF (со штрихкодами).

**Стек:** Go 1.25 · PostgreSQL (pgx/v5) · excelize · pdfcpu · МойСклад API · godotenv

## 2. Команды

```bash
go build ./...          # сборка
go run ./cmd            # запуск
go test ./...           # тесты — ВСЕГДА после изменений
golangci-lint run       # линт (конфиг: .golangci.yml)
```

Перед PR: `go build ./...` + `go test ./...` + `golangci-lint run` — без ошибок.

## 3. Архитектура

Чистая архитектура, зависимости направлены внутрь:

```
cmd/                        — точка входа
app/                        — DI-сборка (app.go, di.go)
internal/
  domain/                   — сущности (order.go)
  usecase/                  — бизнес-логика (orders, sync, export*)
  repository/
    postgres/               — хранение (pgx)
    msapiclient/            — клиент API МойСклад (модели, конвертер, анмаршаллер)
    ordercache/             — кэш заказов
    pdfpreloader/           — предзагрузка PDF
  delivery/
    http/                   — хендлеры, роутер, DTO, мапперы
    web/                    — статика, шаблоны
  exporter/
    excel/                  — экспорт в Excel
    pdf/                    — экспорт в PDF
  msWorkerpool/             — воркерпул + рейт-лимитер для API МойСклад
  config/                   — конфигурация
```

Правила слоёв:
- `domain` не импортирует ничего внутреннего
- `usecase` работает через интерфейсы, не знает про pgx/HTTP
- `delivery` не содержит бизнес-логики — только маппинг и валидация
- Новый код следует этой же структуре

## 4. Workflow — ЖЕЛЕЗНОЕ ПРАВИЛО

- **Никогда не пушить в `main`** — ветка защищена (branch protection, 1 approval)
- **Все изменения только через Pull Request:**
  1. `git checkout main && git pull` — синхронизация
  2. `git checkout -b feat/краткое-описание` (или `fix/...`, `docs/...`)
  3. Изменения → тесты → линт
  4. `git push -u origin HEAD`
  5. PR с описанием: что сделано, как тестировалось, что проверить ревьюеру
- **Merge PR выполняет только владелец репозитория** (или по его явной команде)
- Conventional Commits:
  - `feat:` — новая функциональность
  - `fix:` — исправление бага
  - `refactor:` — рефакторинг без изменения поведения
  - `docs:` — документация
  - `test:` — тесты
  - `chore:` — обслуживание (зависимости, CI)

## 5. Стиль кода

- `gofmt` / `goimports` — обязательно
- Ошибки: `fmt.Errorf("...: %w", err)` — никогда не глотать
- Без `panic` в production-коде; возвращать ошибки
- Интерфейсы определять на стороне потребителя, а не производителя
- Имена: пакеты одним словом без `_`, без camelCase в именах пакетов
- Экспортируемое — документировать комментариями
- Не тащить лишние зависимости; проверять `go mod tidy`

## 6. Ограничения

- **`.env` — не коммитить** (в репо только `.env.example`)
- `blankimport.xlsx` — тестовые данные, не перезаписывать без необходимости
- Моки/поведение API МойСклад не менять без согласования с владельцем
- Не подменять rate-limit логику воркерпула без обсуждения
- Секреты и токены — никогда в код, комментарии, PR-описания

## 7. Тестирование

- Новый функционал — с тестами (`*_test.go`)
- Табличные тесты (table-driven) — предпочтительно
- `go test ./...` должен быть зелёным перед каждым PR
- Для интеграций с внешними API — интерфейсы + mock-заглушки, без реальных запросов в тестах
